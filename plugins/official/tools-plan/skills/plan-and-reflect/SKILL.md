# 何时使用 TODO，何时反思

任务计划（`update_plan` / `read_plan`）与反思（`reflect_plan`）配合使用：
**先用计划把路径显式化，再用反思确保每一步都走在路径上。** 下面是判断时机。

## 何时使用 TODO

### 应该建计划（update_plan）

满足任意一条，就先 `update_plan` 把步骤列出来：

- 任务包含**多个步骤**（预计需要 2 次以上工具调用或动作）；
- 任务需要**跨多轮**推进，或可能在过程中被打断；
- 用户明确要求「制定计划 / 列一下步骤 / 先规划」；
- 任务有清晰可检查的步骤序列（如：读代码 → 改实现 → 跑测试 → 提交）；
- 你发现自己同一轮里越做越多，需要把范围显式化。

### 应该更新计划（update_plan）

- 有步骤**完成**时，把它标成 `done`；
- 正在做的步骤标 `in_progress`；
- 任务范围变化（新增 / 删减 / 调整顺序）时，整体替换步骤列表；
- 发现计划外需求时，**先把它加进计划**，再决定是否执行。

### 应该读计划（read_plan）

- 不确定当前计划是什么时；
- 任务被打断、需要续接时；
- 需要向用户汇报进度时。

### 不需要用 TODO

- 单步、简单任务（如回答一个事实性问题、改一个词）**不需要**建计划；
- 不要为了「显得有计划」而把琐碎步骤写进计划；
- 不要每轮重复 `read_plan` —— 计划已在上下文里时直接继续。

## 何时反思（reflect_plan）

### 动手前反思（推荐带 focus）

在**每轮动手前**（执行下一步动作之前）调用一次 `reflect_plan`，传 `focus` 描述你即将做的动作：

- 命中计划内步骤 → 放心继续；
- 未命中任何步骤 → 可能在做计划外工作，回到计划路径；
- 命中已完成步骤 → 不要重复执行，转向下一步。

特别适合这些场景：

- 长任务进行到一半，检查自己有没有跑偏；
- 刚完成一个大步骤，准备进入下一步时；
- 发现自己开始「顺手做」计划外的事情时；
- 感觉任务范围在膨胀、越做越多时。

### 不需要过度反思

- 简单单步任务不需要反思；
- 每轮动手前调用一次足够，不要在同一轮里反复调用；
- 计划为空时反思没有意义 —— 先 `update_plan` 建计划。

## 推荐节奏

1. **接到多步任务** → `update_plan` 列出步骤。
2. **每轮动手前** → `reflect_plan({ focus: "即将做的动作" })` 确认不跑偏。
3. **步骤完成** → `update_plan` 更新状态（`done` / `in_progress`）。
4. **范围变化** → 先 `update_plan` 调整计划，再继续。
5. **任务收尾** → 最后 `read_plan` 确认全部 `done`，向用户汇报。

## 反模式（看到就停）

- 任务一开始就闷头做，不建计划，越做越散；
- 长任务一路做到底，从不反思，走偏了才发现；
- 每个工具调用前都调 `reflect_plan`，把反思变成噪音；
- 把 trivial 单步任务也写进计划，浪费轮次。
