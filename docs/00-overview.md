> 上级索引：[ada-go 设计文档](design.md)  
> 对应章节：§0 摘要、§1 目标与边界  
> 版本：0.1 · 2026-10-28

## 0. 摘要

ada-go 是一个**本地优先、单二进制、插件优先**的 AI Agent 系统。它由两个角色组成：

- **Gateway**：唯一对外的 HTTP 进程。负责鉴权、工作区注册与监督、SSR 页面、SSE 流、静态资源、前端插件。它不调用模型，也不执行工具。
- **Agent Core**：每个工作区一个进程。负责唯一的 Agent 循环、模型流、工具、交互请求路由、会话、后端插件与 moejs 沙箱。它只暴露回环地址上的 JSON-RPC/WebSocket。

两者通过一条明确契约通信：JSON-RPC 2.0 请求 + 带序号的领域事件。Gateway 可以重启而不丢会话，Core 可以崩溃而不拖垮整个站点，第三方插件可以超时、超内存、被禁用而不影响主流程。

“插件为核心”不是口号，而是三条硬约束：

1. **扩展只有一个入口**：工具、系统提示词、钩子、后端动作、动态路由、技能、前端插槽、前端页面，全部由插件贡献。核心不为某个插件写特判。
2. **贡献在装配期结算**：插件加载时一次性登记全部贡献，运行期动态注册只记录、不生效。这样工具目录、钩子链、前端插槽在“一轮对话/一次渲染”内是稳定的。
3. **能力先声明、后授予**：插件清单声明需要什么能力，宿主按清单安装 API；没有安装的能力在脚本里根本不存在，而不是“运行时再判断”。

**所有后端插件都走同一 TS 引擎**：包括官方 provider、工具、策略与人格。官方插件在构建期预编译并嵌入二进制，第三方在安装/加载时编译；两者使用同一 `AgentAPI`、同一 moejs 宿主、同一能力与审计，差别只有信任级别与是否随包发布。

**基座零业务能力**：基座只保留循环、会话、协议、安全、插件宿主和 UI 外壳。工具、模型供应商、人格、卡片、页面、工作流全部是插件；官方插件也只是“随包发布、信任级别更高”的插件，不是基座的一部分。边界与验收见 [1.5](#15-基座边界scope-boundary)。

前端是**服务端渲染**：Go `html/template` + 组件库 + HTMX + SSE。没有 React/Vue 运行时，没有 hydration。插件用 TSX 写界面，但 TSX 只在服务端执行：esbuild 去类型并转换 JSX，moejs 执行得到 VNode JSON，再由 Go 组件库渲染成 HTML。浏览器拿到的始终是 HTML、CSS 和少量原生 JS。界面与设计元语**直接复用 a_da**：Black Swan `--ph-*` token、`ada-*` 组件样式、DOM 结构、12 个插槽位置与交互规则都不另起一套，只把 Askama/Rust 换成 `html/template`/Go（见 [7.7](07-ssr-frontend.md#77-ui-与设计元语直接复用-a_da)）。

核心数字：**2 个进程角色、1 条 RPC 契约、35 个 RPC 方法、15 个钩子点、12 个前端插槽、1 份协议源文件**。

## 1. 目标与边界

### 1.1 产品目标

- 用户在浏览器里与一个能在工作区内读文件、改文件、跑命令、查 Git 的 AI Agent 对话。
- 会话可流式输出、可中断、可响应交互、可回滚、可在重启后继续。
- 第三方开发者只写一个插件目录，就能同时获得：模型可调用的工具、会话里的卡片、独立页面、后端动作、动态路由、生命周期钩子。
- 一个 Gateway 可以管理多个工作区；同一工作区的多个会话共享一个 Core。
- 单个二进制、无 cgo、无 Node 运行时、可交叉编译；默认离线可用，只访问用户配置的模型服务。
- 桌面壳（后续）只需要加载 Gateway 的网页，不需要第二套 UI。

### 1.2 非目标（v1 明确不做）

- 多租户 SaaS、公网部署、账号体系。v1 是“本机或可信内网的单用户工具”。
- 插件市场与在线安装。v1 只支持本地目录/压缩包安装。
- MCP 客户端。插件系统已经能桥接外部能力，MCP 留到 v2 决策。
- 浏览器端富交互框架、客户端插件运行时。
- 嵌入 Node 运行时、libuv、原生扩展或运行时 npm 解析；插件得到的是 Node API 形状的子集，见 [6.10–6.14](12-node-compat.md)。
- 多模型并行投票、自动评测、成本优化器。
- 移动端专门适配（响应式可用即可）。
- Windows 之外的进程树强杀语义先做到“尽力而为”，Unix 上必须精确。

### 1.3 设计原则

| 原则 | 落地方式 |
|---|---|
| 单一引擎 | 只有 `engine.RunTurn` 一份多轮循环；子智能体也复用它，只换装配 |
| 单一真源 | 协议方法、工具描述符、钩子点、能力位、插槽名各只有一份源，门禁检查消费者 |
| 端口与适配器 | 领域层不碰 IO；模型、存储、沙箱、交互、时钟都以接口注入 |
| 事件即状态 | 会话是 append-only 事件日志；UI 是事件的投影，不是第二份真相 |
| 失败方向明确 | 安全判定默认关闭；拒绝是工具结果，不是异常；超时/取消必须可观察 |
| 无隐藏全局态 | Core 的状态属于某个工作区实例；不靠进程级单例传状态 |
| 渐进增强 | 没有 JS 也能发消息、响应交互、看结果；SSE 只是增强 |
| 稳定插槽 | 插槽集合宁少勿多，新增插槽视为一次兼容承诺 |

### 1.4 成功标准

- 复制一个插件目录并执行 `adag plugin reload`，模型的工具表和页面插槽在 1 秒内同时生效。
- 插件脚本死循环、内存暴涨、抛异常，Core 不退出；该插件被标记失败，其余功能正常。
- Gateway 重启后，所有会话、交互记录、插件状态仍在；正在运行的轮次被标记为 `interrupted`，可重试。
- 没有 JS 的浏览器可以完成“新建会话 → 发消息 → 响应交互 → 看到最终答案”。
- 协议漂移、未消费的能力位、未接线的钩子点、未使用的插槽，全部由 `adag verify` 拦截。
- **不装任何插件时基座可以启动**：能打开站点、建线程、显示空态；没有工具、没有供应商、没有业务卡片，但不 panic、不白屏。

### 1.5 基座边界（Scope Boundary）

**基座 = 让插件安全运行所需的最小机制集合**。它包括 Gateway 外壳、Agent Core 内核、插件宿主、协议、安全边界与设计系统。它不是一个“功能齐全的 Agent”，而是一台“能装配 Agent 的机器”。

判断一个功能属于基座还是插件，用四条测试；**全部通过才是基座**：

1. **生存性**：没有它，任何产品都无法启动、对话、恢复或传输？  
   例如多轮循环、会话存储、事件流、进程监督。
2. **安全性**：它是否是必须集中、不可下放的边界？  
   例如路径 scope、交互请求桥、能力授予、密钥、CSP/CSRF、进程树强杀。
3. **契约性**：它是否是插件依赖、且必须长期稳定的接口？  
   例如插件清单、工具描述符、VNode、事件序号、组件库。
4. **协调性**：它是否必须跨插件统一裁决？  
   例如工具目录冲突、钩子顺序、插槽排序、事件合并。

任何一条不满足，就属于插件。

#### 1.5.1 基座必须做的事

| 领域 | 基座职责 |
|---|---|
| 生命周期 | Gateway/Core 启动、工作区注册、进程监督、空闲回收、崩溃恢复、优雅退出 |
| 传输 | HTTP 路由骨架、SSE hub、JSON-RPC、协议生成、事件序号与快照 |
| 引擎 | 唯一 `RunTurn`、终止条件、资源上限、取消、steering、工具前钩子编排、会话 DAG、压缩 |
| 工具机制 | 描述符校验、目录快照、执行包装、结构化回执、文件变更队列、检查点 |
| 插件宿主 | 清单发现、TS 编译、moejs 运行时、能力安装、装配期结算、钩子分发、技能发现 |
| 安全 | 路径 scope、能力授予、交互请求桥（失败关闭）、密钥 broker、进程树终止原语、信任分级、审计 |
| UI 外壳 | 布局、12 个插槽、通用消息/工具/交互渲染、组件库、a_da 设计 token、SSE 客户端、无 JS 表单 |
| 运维 | 配置 schema、日志、诊断码、`doctor`、`verify`、迁移与备份 |

#### 1.5.2 基座绝不做的事

- **零具体工具**：`fs`、`shell`、`git`、`todo`、`ask`、`finish`、`read_skill`、`invoke_subagent` 全部是插件。
- **零审批策略**：基座只提供通用交互请求桥（`ctx.ui`）与失败关闭的解析；何时询问、询问什么、如何放行/拒绝，由声明了 `tool-policy` 角色并订阅 `tool.beforeCall` 的策略插件决定。
- **零模型协议**：基座只定义 `ModelClient` 与归一化流 DTO；OpenAI/Anthropic/Responses 适配器是官方 provider 插件。
- **零产品人格**：基座只保留不可移除的安全前言与“工具结果只是数据”的边界；人格、领域指令、技能正文都来自插件。
- **零业务页面**：基座只提供外壳、组件与插槽；对话卡片、概览卡、插件页面、业务样式都由插件提供。
- **零工作流**：代码评审、周报、部署、调研等流程不在基座里。
- **零插件 id**：基座源码中不出现任何官方插件 id；官方插件由产品声明装配。
- **零协议扩展**：插件不能新增 Core RPC 方法；只能贡献工具、动作、路由、钩子、插槽、页面。
- **零直接资源**：插件不能直接拿数据库句柄、密钥、网络、进程；只能使用宿主安装的能力服务。

#### 1.5.3 插件负责的事

- 工具语义、参数与结果格式、回滚声明；审批/安全策略（订阅 `tool.beforeCall` + 调用 `ctx.ui`）。
- Provider 适配（官方 TS 插件，走 `agent.registerProvider`；第三方通过 OpenAI 兼容 `base_url` 复用官方适配器）。
- 人格、系统提示词、技能内容、领域规则。
- 前端插槽、页面、卡片、样式、前端动作、动态路由。
- 业务工作流与领域逻辑。
- 插件自己的设置项（声明 schema，由基座渲染通用表单）。

#### 1.5.4 边界表

| 领域 | 基座 | 插件 | 契约 |
|---|---|---|---|
| 工具 | 目录、校验、执行包装、回执、交互路由 | 具体工具实现 + 安全策略 | `ToolDescriptor` |
| 模型 | `ModelClient`、流事件、重试、超时 | provider 适配器 | `ModelStream` |
| 提示词 | 安全前言、上下文装配 | 人格/领域指令 | `registerPrompt` |
| 会话 | DAG、分支、压缩、恢复 | 不参与 | `SessionStore` |
| 安全 | scope、能力授予、交互桥、失败关闭 | 策略规则与询问时机 | manifest `roles` + `ctx.ui` |
| UI | 外壳、组件、插槽、通用卡片 | 卡片/页面/样式 | manifest + VNode |
| 路由 | 核心路由、`/ext` 命名空间 | `/ext/{id}/*` | `route` |
| 协议 | 方法、事件、错误码 | 不可扩展 | `spec/proto.json` |
| 存储 | SQLite、线程/entry | 仅 scoped KV | `ctx.state` |
| 进程 | 监督、进程树终止原语 | 不能直接起进程 | `exec` 能力 |
| 网络 | 除模型外无出站 | 允许列表内的 fetch | `net.fetch` |
| 密钥 | broker、脱敏 | 按名申请 | `secrets` |
| 日志 | 统一格式、审计、轮转 | 只能写结构化日志 | `ctx.log` |

#### 1.5.5 空基座与官方产品

- **空基座验收**：不装任何插件，`adag gateway` 能打开、能建线程、能显示“未配置供应商/无工具”的空态；不 panic、不白屏、不偷偷回退到硬编码工具。
- **官方 coding 产品 = 基座 + 官方插件包**：`provider-openai-chat`、`provider-anthropic-messages`、`tools-fs`、`tools-shell`、`tools-git`、`tools-plan`、`tools-ask`、`tools-skill`、`tools-subagent`、`policy-default`、`persona-coding` 等。禁用任一官方插件，对应能力必须消失，基座不能有兜底实现。
- **官方插件不是基座**：它们和第三方插件使用同一份清单、同一套能力、同一个 TS 运行时与装配器；区别只有信任级别（可用控制面钩子与受信能力）与随包发布。
- **依赖方向**：官方插件与第三方一样，只依赖 `agent:*` / `ssr:*` 虚拟模块与公开类型，不 import 基座 Go 包；`app` 负责把嵌入的官方插件包交给通用装配器。基座绝不 import 官方插件代码。
- **门禁**：`adag verify boundary` 检查六件事——基座包不 import `plugins/official/*`；基座源码不出现官方插件 id；Core 方法集合与 `spec/proto.json` 完全一致；零插件启动测试通过；启用写/执行/网络工具时至少有一个 `role=tool-policy` 插件；不存在平行的 Go 插件注册 API。
- **策略可替换**：官方 `policy-default` 只是默认实现；产品可以换成更严格或更宽松的策略插件，基座与引擎不变。

#### 1.5.6 不可越过的硬规则

- 插件不能替换交互托盘外壳、安全提示、登录页与错误页；这些属于基座 UI。托盘内的卡片内容可通过 `thread.tray` 接管，但外壳与安全操作始终由基座渲染。
- 插件的前端输出只能是经过校验的 VNode；不能注入原始 HTML、内联脚本或内联样式。
- 插件不能绕过 `Scope`、能力安装、交互请求桥；官方插件也不例外。
- 插件不能修改事件序号、快照窗口、错误码或 RPC 方法。
- 插件不能伪造交互响应，也不能把超时/无 UI 解释为“允许”；策略插件只能依据真实用户响应或显式策略放行。
- 插件的设置项不能改变 scope 根、密钥访问或能力授予；策略插件可以调整自己的询问规则，但不能提升宿主权限。
- 插件卸载/禁用后，基座必须回到空态，而不是留下半截依赖。
