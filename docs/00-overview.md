# 摘要与基座边界

> 上级索引：[ada-go 设计文档](design.md)  
> 对应章节：§0 摘要、§1 目标与边界  
> 版本：0.3 · 2026-11-10

## 0. 摘要

ada-go 是一个**本地优先、单二进制、插件优先**的 AI Agent 系统。它由两个角色组成：

- **Gateway**：唯一对外的 HTTP 进程。负责鉴权、工作区注册与监督、SSR 页面、SSE 流、静态资源、前端插件渲染。它不调用模型，也不执行工具。
- **Agent Core**：每个工作区一个进程。负责唯一的 Agent 循环、模型流、工具、交互请求路由、会话、后端插件与 moejs 沙箱。它只暴露回环地址上的 JSON-RPC/WebSocket。

三条不可动摇的架构约束：

1. **单一引擎**：只有 `engine.RunTurn` 一份多轮循环；子智能体复用同一入口，只换装配。
2. **能力先声明、后校验**：插件清单可以声明能力词汇，宿主校验名字与最低信任级别；但**能力位不再决定「装什么」**（2026-11-10 决策）——宿主对系统插件与第三方安装同一套桥与模块。
3. **基座零业务语义、零产品兜底**：基座只保留内核、通用原语、安全/契约边界与 UI 外壳；工具、provider、人格、页面、定时任务、环境变量、供应商配置与用量展示全部由插件实现；随包发布、builtin 信任的是**系统插件**，不是基座，禁用后对应能力必须消失。

所有后端插件都走同一 TS 引擎：包括系统 provider、工具、cron、env 与人格。系统插件在构建期预编译成 `dist/`，运行时从 `plugins/official`（Electron resources）加载；第三方插件在安装/加载时编译。两者使用同一 `AgentAPI`、同一 moejs 宿主、同一套桥与审计；差别只有信任级别与控制面钩子权限。

前端是**单页面应用（SPA，2026-11-11 起）**：Go 只渲染 shell（bootstrap JSON），页面由自研运行时 `static/ada/` 在浏览器渲染；插件前端是运行时装载的 SFC 单文件组件（零构建、无 SSR，详见 [SPA 提案](../proposals/spa-frontend-framework.md)）。历史上是 Go `html/template` 整页 SSR + TSX 服务端渲染 + 交互岛（见 docs/07/14 的状态横幅）。界面与设计元语直接复用 a_da：Black Swan `--ph-*` token、`ada-*` 组件样式、DOM 结构、12 个插槽位置与交互规则；模型生成内容仍走服务端校验的 VNode JSON（display profile）。

核心数字：**2 个进程角色、1 条 RPC 契约、33 个 RPC 方法、14 个钩子点、12 个前端插槽、1 份协议源文件**。

## 1. 目标与边界

### 1.1 产品目标

- 用户在浏览器里与一个能在工作区内读文件、改文件、跑命令、查 Git 的 AI Agent 对话。
- 会话可流式输出、可中断、可响应交互、可回滚、可在重启后继续。
- 第三方开发者只写一个插件目录，就能同时获得：模型可调用的工具、会话里的卡片、独立页面、后端动作、动态路由、生命周期钩子、可选的客户端岛。
- 一个 Gateway 可以管理多个工作区；同一工作区的多个会话共享一个 Core。
- 单个二进制、无 cgo、无 Node 运行时、可交叉编译；默认离线可用，只访问用户配置的模型服务。
- 桌面壳（后续）只需要加载 Gateway 的网页，不需要第二套 UI。

### 1.2 非目标（v1 明确不做）

- 多租户 SaaS、公网部署、账号体系。v1 是“本机或可信内网的单用户工具”。
- 插件市场与在线安装。v1 只支持本地目录/压缩包安装。
- 嵌入 Node 运行时、libuv、原生扩展或运行时 npm 解析；插件得到的是 Node API 形状的子集，见 [12](12-node-compat.md)。
- 多模型并行投票、自动评测、成本优化器。
- 移动端专门适配（响应式可用即可）。
- Windows 之外的进程树强杀语义先做到“尽力而为”，Unix 上必须精确。

MCP 不在基座内置；v2 以普通系统插件 `mcp-client` 接入，见 [15 §18](15-extensions.md)。

### 1.3 设计原则

| 原则 | 落地方式 |
|---|---|
| 单一引擎 | 只有 `engine.RunTurn` 一份多轮循环；子智能体也复用它，只换装配 |
| 单一真源 | 协议方法、工具描述符、钩子点、插槽名、能力位词汇各只有一份源，门禁检查消费者 |
| 端口与适配器 | 领域层不碰 IO；模型、存储、沙箱、交互、时钟都以接口注入 |
| 事件即状态 | 会话是 append-only 事件日志；UI 是事件的投影，不是第二份真相 |
| 失败方向明确 | 交互失败方向明确（`timeout`/`unavailable` 由调用方按拒绝处理）；拒绝是工具结果，不是异常；超时/取消必须可观察 |
| 无隐藏全局态 | Core 的状态属于某个工作区实例；不靠进程级单例传状态 |
| 渐进增强 | **2026-11-11 起有意放弃（SPA）**：仅登录/错误页保留无 JS 可用；无 JS 的兜底能力由登录页与错误页承担 |
| 稳定插槽 | 插槽集合宁少勿多，新增插槽视为一次兼容承诺 |
| 零业务语义 | 基座不读产品数据文件、不提供产品端点、不解释业务规则 |
| 零产品兜底 | 禁用系统插件后能力消失；基座不偷偷补一个同名实现 |
| 内核默认 + 可替换 | 内核机制默认有 Go 实现，同时保留受控 seam；替换实现必须通过契约测试 |
| 文档收敛 | 不新增独立计划/评估/交付文档；设计正文保持 16 份，细节并入现有章节 |

### 1.4 成功标准

- 复制一个插件目录并执行 `adag plugin reload`，模型的工具表和页面插槽在 1 秒内同时生效。
- 插件脚本死循环、内存暴涨、抛异常，Core 不退出；该插件被标记失败，其余功能正常。
- Gateway 重启后，所有会话、交互记录、插件状态仍在；正在运行的轮次被标记为 `interrupted`，可重试。
- 没有 JS 的浏览器可以完成“新建会话 → 发消息 → 响应交互 → 看到最终答案”。
- 协议漂移、能力名越界、未接线的钩子点、未使用的插槽，全部由 `adag verify` 拦截。
- **不装任何插件时基座可以启动**：能打开站点、建线程、显示空态；没有工具、没有供应商、没有业务卡片，但不 panic、不白屏。
- **删除测试通过**：禁用任一系统插件后，对应功能、数据入口与后台行为一起消失，基座不补位。

### 1.5 基座边界（Scope Boundary）

**基座 = 让插件安全运行所需的最小机制集合**。它包括 Gateway 外壳、Agent Core 内核、插件宿主、协议、安全边界与设计系统。它不是一个“功能齐全的 Agent”，而是一台“能装配 Agent 的机器”。

判断一个功能属于基座还是插件，用四条测试；**全部通过才是基座**：

1. **生存性**：没有它，任何产品都无法启动、对话、恢复或传输？例如多轮循环、会话存储、事件流、进程监督。
2. **安全性**：它是否是必须集中、不可下放的边界？例如路径 scope、交互请求桥、能力授予、密钥、CSP/CSRF、进程树强杀。
3. **契约性**：它是否是插件依赖、且必须长期稳定的接口？例如插件清单、工具描述符、VNode、事件序号、组件库。
4. **协调性**：它是否必须跨插件统一裁决？例如工具目录冲突、钩子顺序、插槽排序、事件合并。

任何一条不满足，就属于插件。再补四条工程判据：

5. **热路径**：是否在每 token、每轮次、每工具调用的关键路径上？是则留在内核。
6. **数据归属**：是否需要机器级、跨工作区、长期持久化？若是，基座只能提供通用存储原语，语义归系统插件。
7. **启动顺序**：零插件时是否必须存在？插件管理器、模型解析、UI 外壳、存储必须先存在。
8. **删除测试**：禁用插件后功能是否仍然从基座可用？是则说明它还不是插件。

#### 1.5.1 基座必须做的事

| 领域 | 基座职责 |
|---|---|
| 生命周期 | Gateway/Core 启动、工作区注册、进程监督、空闲回收、崩溃恢复、优雅退出 |
| 传输 | HTTP 路由骨架、SSE hub、JSON-RPC、协议生成、事件序号与快照 |
| 引擎 | 唯一 `RunTurn`、终止条件、资源上限、取消、steering、钩子分发、会话 DAG、压缩（默认实现 + seam） |
| 工具机制 | 描述符校验、目录快照、执行包装、结构化回执、文件变更队列、检查点 |
| 插件宿主 | 清单发现、TS 编译、moejs 运行时、模块与上下文注入、装配期结算、钩子分发、技能发现 |
| 安全 | 路径 scope、交互请求桥、密钥 broker、进程树终止原语、信任分级、审计 |
| 通用原语 | `ctx.fs`、`ctx.fetch`、`ctx.exec`、`ctx.process`、`ctx.state`、`ctx.config`、`ctx.events`、`ctx.ui`、`ctx.secret` |
| UI 外壳 | 布局、12 个插槽、通用消息/工具/交互渲染、组件库、a_da 设计 token、SSE 客户端、无 JS 表单 |
| 运维 | 配置 schema、日志、诊断码、`doctor`、`verify`、迁移与备份 |

#### 1.5.2 基座绝不做的事

- **零具体工具**：`fs`、`shell`、`git`、`todo`、`ask`、`finish`、`invoke_subagent`、`find_tool`/`exec_tool` 全部是系统插件。
- **零审批策略**：审批策略已整体移除（2026-11-10 决策）。基座只保留通用交互桥（`ctx.ui`）；它不判定该问什么、也不在执行前拦截任何工具调用——写/执行工具直接执行。要加前置约束，只能落到工具实现自己。
- **零模型协议**：基座只定义 `ModelClient` 与归一化流 DTO；OpenAI/Anthropic/Responses 适配器是系统 provider 插件。
- **零产品人格**：基座只保留不可移除的安全前言与“工具结果只是数据”的边界；人格、领域指令、技能正文都来自插件。
- **零定时任务语义**：基座不读 `cron.json`、不解析 cron 表达式、不调度任务、不提供 `/api/cron/fire`；cron 是系统插件。
- **零环境变量管理语义**：基座只提供“向子进程注入已配置环境”的通用能力；`~/.adago/env.json` 的格式、校验、管理页归 env 系统插件。
- **零供应商配置管理**：基座只解析“当前模型 + 供应商配置视图”并发起请求；供应商/模型的 CRUD、拉取 `/models` 归 provider-admin 系统插件。
- **零用量聚合/展示**：基座只记录每轮原始 token/成本事件；聚合、卡片、页面归 token-usage / composer-telemetry 系统插件。
- **零业务页面**：基座只提供外壳、组件与插槽；对话卡片、概览卡、插件页面、业务样式都由插件提供。
- **零工作流**：代码评审、周报、部署、调研等流程不在基座里。
- **零插件 id**：基座源码中不出现任何系统插件 id；系统插件由产品声明装配。
- **零协议扩展**：插件不能新增 Core RPC 方法；只能贡献工具、动作、路由、钩子、插槽、页面。
- **零直接资源**：插件不能直接拿数据库句柄、密钥、网络、进程；只能使用宿主注入的桥。

#### 1.5.3 系统插件层

系统插件（system plugin）是**随产品发布、`trust=builtin`、可禁用、无基座兜底**的插件。它们与第三方使用同一份清单、同一个 moejs 宿主与同一套 `AgentAPI`；区别只有信任级别、随包发布与产品声明。

| 类别 | 系统插件 | 拥有的业务语义 |
|---|---|---|
| Provider | `provider-openai-chat`、`provider-anthropic-messages`、`provider-openai-responses` | 协议适配、流解析、鉴权头、模型能力声明 |
| 工具 | `tools-fs`、`tools-shell`、`tools-git`、`tools-plan`、`tools-ask`、`tools-skill`、`tools-subagent` | 具体工具的参数、结果、回滚声明与交互语义 |
| 工具发现 | `tool-discovery`（`find_tool`/`exec_tool`） | 目录只读投影与按名执行；内层执行沿用同一套超时与循环检测 |
| 人格 | `persona-coding` | 系统提示词片段与领域规则 |
| 定时任务 | `cron-manager` | cron 表达式、任务模型、调度循环、运行历史、到期触发 |
| 环境变量 | `env-manager` | env 命名空间、校验、管理页与子进程注入策略 |
| 供应商管理 | `provider-admin` | 供应商/端点/API Key/模型清单的 CRUD 与页面 |
| 用量/遥测 | `token-usage`、`composer-telemetry` | 聚合、卡片、页面、上下文环与轮询节奏 |
| 外部工具 | `mcp-client`、`browser-use` | MCP / browser-use 协议与工具映射 |
| 插件管理 | `plugin-helper` | 插件脚手架与安装桥调用 |
| 示例/图表 | `ui-charts`、`ui-hello` | 图表块（模型内容）；SFC 插件参考示例（运行时装载） |

表中的业务语义**不得回落到基座**。例如禁用 `cron-manager` 后，不应再有任务被调度；禁用 `env-manager` 后，不应再出现 env 管理入口；禁用 `token-usage` 后，基座不应继续渲染用量页。

#### 1.5.4 内核默认实现与可替换 seam

内核不是“不可替换的黑盒”，而是**默认实现 + 受控 seam**：

- 每个内核机制都有生产实现（SQLite、`ModelCompactor`、`toolkit.Executor`、moejs 宿主等）和稳定接口（端口/消费方定义接口）。
- 替换实现只能在装配期注入，不能在运行期热替换；替换者必须通过对应契约测试与安全不变量。
- 安全不变量不可替换：路径 scope、交互失败方向、进程树终止、审计、VNode 白名单。
- 插件通过 `agent:*` 贡献面扩展；需要替换内核机制时，走 seam + 装配，不新增插件 hook 的“超级权限”。

seam 清单与替换规则见 [06 §6.10](06-plugin-runtime.md#610-内核实现与替换-seam)。

#### 1.5.5 第三方前端同面

第三方插件与系统插件使用**同一前端贡献面**：`slots`、`pages`、`nav`、`dashboard`、`blocks`、`actions`、`route`、`styles`、`scripts`、`assets`、`client`、`hydrate`、`clientOnly`。

- 前端脚本/客户端 bundle 需在清单声明 `frontend.script`；只读预取需要 `backend.read`。
- 安装/首次启用时展示声明的能力与脚本风险，用户显式确认后才装配。
- CSP 仍为 `script-src 'self'`；同源脚本是已知风险，后续可选 iframe/Worker 隔离，不作为 v1 前置。
- 渲染仍只接受 VNode；插件拿不到 `template.HTML`，不能注入原始 HTML/内联脚本/内联样式。

实现边界见 [07 §7.5](07-ssr-frontend.md#75-前端插件化) 与 [14](14-ui-runtime.md)。

#### 1.5.6 空基座与删除测试

- **空基座验收**：不装任何插件，`adag gateway` 能打开、能建线程、能显示“未配置供应商/无工具”的空态；不 panic、不白屏、不偷偷回退到硬编码工具。
- **删除测试**：对每个系统插件，禁用/删除后必须同时满足：模型工具表/页面/导航/后台行为消失；基座不补位；数据入口不再由基座提供。
- **官方产品 = 基座 + 系统插件包**：coding 产品声明见 [products/coding.agent.json](../products/coding.agent.json)。禁用任一系统插件，对应能力必须消失。

#### 1.5.7 不可越过的硬规则

- 插件不能替换交互托盘外壳、安全提示、登录页与错误页；这些属于基座 UI。托盘内的卡片内容可通过 `thread.tray` 接管，但外壳与安全操作始终由基座渲染。
- 插件的前端输出只能是经过校验的 VNode；不能注入原始 HTML、内联脚本或内联样式。
- 插件不能绕过 `Scope`、交互请求桥；系统插件也不例外。例外（2026-10-31 决策）：`ctx.fs` 的读成员允许宿主绝对路径，写入与 `exec` 的 cwd 仍受 `Scope` 约束。
- 插件不能修改事件序号、快照窗口、错误码或 RPC 方法。
- 插件不能伪造交互响应，也不能把超时/无 UI 解释为“允许”；工具实现只能依据真实用户响应，或明确返回 `denied` 回执。
- 插件的设置项不能改变 scope 根、密钥访问或宿主权限；审批策略已移除，没有任何插件能拿到「执行前放行/拒绝」的钩子。
- 插件卸载/禁用后，基座必须回到空态，而不是留下半截依赖。

### 1.6 已钉定的方向（2026-11-09）

| 决策 | 取值 |
|---|---|
| 目标 | 基座零业务语义、零产品兜底；产品功能由系统插件实现 |
| cron | cron 是系统插件，不是基础设施；基座不调度、不读任务文件 |
| 新增原语 | 新增 `global.config`（机器级命名空间配置）与 `events.read`（只读事件/用量查询） |
| 第三方前端 | 与系统插件同面；用安装确认、`frontend.script` 声明、CSP 与审计控制风险 |
| 内核 | 保留 Go 默认实现，同时保留可替换 seam；替换必须过契约测试与安全不变量 |
| 文档 | 设计正文收敛为 16 份；计划/评估/交付说明并入 10/11 与对应章节 |
